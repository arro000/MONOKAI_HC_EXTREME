# Bash highlighting analysis

## Verified classification

The built-in shellscript extension registers `source.shell`, using a grammar derived from Better Shell Syntax. Actual fixtures were tokenized; Bash highlighting here is TextMate-based.

- Names in expansions use `variable.other.normal.shell`.
- `$1`/`$@` use positional parameter scopes; `$?`, `$$`, `$#`, `$*` and `$!` use `variable.language.special.shell`.
- `$(...)` uses `meta.scope.subshell`, without a `.shell` suffix.
- Builtins use `support.function.builtin.shell`; external commands and user function invocations share command/function-call scopes.
- Flags can use `constant.other.option` without a language suffix. Heredoc scopes can have dynamic delimiter names.

## Integrated rules

Variable names are cyan, positional parameters and flags orange, special parameters and expansion delimiters purple. Function declarations/external calls are green, lexically recognized builtin commands cyan, command separators pink. Embedded command/arithmetic bodies reset the inherited string color. Heredoc labels and shebangs are cyan.

Longer scope selectors preserve the delimiter color when `$` is classified with both punctuation and variable scopes. Prefix selectors qualified by `source.shell` cover suffixless flags and dynamic heredoc labels.

## Recognition details

Quoted heredoc delimiters disable interpolation, including double-quoted delimiters. The fallback text in `${name:-guest}` shares the variable-name scope. The grammar's builtin list is lexical and cannot recognize shadowed commands.

The installed grammar misclassifies some `$((...))` arithmetic expansions as subshells, although `((...))` statements have arithmetic scopes. Regex patterns following `=~` are also only partially recognized. The theme styles the supplied tokens; it does not replace the shell grammar.

Example: [`examples/bash/preview.sh`](../../examples/bash/preview.sh), syntax-checked with `bash -n`.
